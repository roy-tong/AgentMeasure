01 — The problem

The software consumer changed.
The measurement stack didn’t.

A capability passes through many states between existing and creating value. Most telemetry collapses them into one vague number: “tool usage.”

Available≠Presented
Presented≠Selected
Selected≠Used
Used≠Useful
Useful≠Incremental Value
Measured Usage≠Billable Usage

Three attempts of one operation are not three billable operations — unless the metering policy says so.

Agent systems collapse these states into vague “tool usage.”
AgentMeasure keeps them separate.

02 — The measurement stack

From reach to value.

Metric families, not a universal KPI. A search capability, a booking API, and a compute job have different value structures — the same facts map onto all of them.

01 Reach Did the capability enter the choice set? Defined
02 Choice Was it selected? Defined
03 Use Was it actually executed? Defined
04 Utility Was the result consumed? Partial
05 Value Did it improve the outcome? Draft

We do not pretend everything is already measurable. The evidence boundary — defined, partial, draft — is part of the design, stated on every number.

03 — Claim discipline

Similar events. Different facts.

Three distinctions most telemetry stacks blur — and AgentMeasure refuses to.

01

Attempt ≠ Operation

1 intent
↓
Attempt 01 ✕
Attempt 02 ✓
↓
= 1 Operation

Attempts are execution facts. Operations are logical intents. Retries are multiple attempts of one operation — mixing the two is how agent reliability reports get distorted.

02

Returned ≠ Consumed

Tool returned result
↓
?
Did the caller actually use it?
RETURNEDobservable
CONSUMEDneeds evidence

Unknown is a valid, first-class answer. AgentMeasure never records unverified consumption — the field stays UNKNOWN until evidence exists.

03

Observed choice ≠ Preference

selected_by:
model · router · policy
workflow · user · platform
↓
what happened ≠ why

A selection can be made by the model, a router, a workflow, the user, or a policy. AgentMeasure records what happened before inferring why.

01

No agent-side install

Third-party agents never need AgentMeasure. Measurement happens where the capability is delivered.

02

Provider-side measurement

The SDK wraps your tool handlers and emits canonical observations — one schema, six payload classes.

03

Not on the critical path

Non-blocking, durable spool with loss accounting. If the SDK fails, your server doesn’t.

04

Your data can stay local

JSONL on your machine, analytics generated locally. Hosted ingestion is explicit opt-in, later.

MCP is not required — it is the first reference surface. Your software does not need to be open source.

08 — Why this matters

Software is becoming callable.

Human Software Economy
Human↓ UI↓ App↓ Seat / Month
Agent Capability Economy
Agent↓ Capability↓ Execution↓ Outcome↓ Usage · Value · Transaction

Before capabilities can be priced, compared, or purchased by agents,
they need a shared measurement layer.

That layer is the foundation for Capability as a Service. AgentMeasure standardizes economic facts — not money movement. Payment rails stay with existing payment infrastructure.
